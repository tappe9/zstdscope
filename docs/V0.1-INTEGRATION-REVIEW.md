## Issue #31 findings and remediation

### Frame Content Size consistency

The original parser decoded Frame Content Size but did not compare it with decoded-size information derivable from the parsed block sequence. Some hand-built FCS-width fixtures therefore declared 256 decoded bytes while containing an empty Raw block and were incorrectly treated as complete valid frames.

PR #32 adds checked decoded-size bounds:

- Raw contributes exactly `Block_Size`;
- RLE contributes exactly `Block_Size`;
- Compressed contributes `0..=Block_Maximum_Size` because internals remain opaque.

A present FCS outside the accumulated bounds is now rejected with a typed `FrameContentSizeMismatch` error. Raw/RLE-only frames therefore require exact equality. The affected FCS fixtures now use an RLE block with a decoded repetition count matching the declared FCS.

### Minimum Compressed Block envelope

Compressed payload internals remain opaque, but a Compressed Block still requires room for a Literals Section header and the Sequences Section `Number_of_Sequences` field. PR #32 rejects Compressed `Block_Size` 0 and 1 with `InvalidCompressedBlockSize` without decoding compressed internals.

### CLI output robustness

The text renderer now writes through `std::io::Write` instead of constructing a complete output `String`. JSON uses `serde_json::to_writer_pretty` directly. Output failures are represented as CLI errors rather than panics, and a downstream normal pipe closure (`BrokenPipe`) terminates successfully.

Parse and input I/O failures continue to return non-zero status, write diagnostics to stderr, and do not emit partial-success JSON.

### Fixture provenance and classification

Reference fixtures generated with official Zstandard CLI v1.5.7 remain the fully valid end-to-end corpus. Regeneration instructions now include `zstd --test`.

Hand-built fixtures explicitly distinguish:

- complete frames whose understood structural invariants are internally consistent;
- envelope-only samples such as opaque Compressed payload or arbitrary stored checksum cases;
- intentionally malformed/boundary inputs.

The official decoder remains a useful differential/reference tool, not the sole specification oracle, because it can intentionally be more permissive than the published format.

### Documentation and rustdoc

`README.md`, `README.ja.md`, `CONTRIBUTING.md`, fixture documentation, and `docs/ZSTD-FORMAT.md` now state the actual v0.1 validation boundary.

The CLI binary target has rustdoc generation disabled and CI documents the public library explicitly, removing the previous lib/bin `zstdscope` rustdoc output collision.

### Package/release gates

CI now includes:

```bash
cargo package -p zstdscope --list
cargo publish -p zstdscope --dry-run
```

The first crates.io package target is the reusable `zstdscope` library. `zstdscope-cli` remains `publish = false`; CLI binary distribution is intentionally separate and deferred. Because this PR does not establish a released CLI binary build pipeline, committing a workspace `Cargo.lock` is not a v0.1 library-release blocker.

## Known v0.1 limitations

These remain deliberate boundaries rather than blockers for the first library pre-release:

- no compression or decompression;
- Compressed Block internals remain opaque beyond outer structural validation;
- stored content checksums are not verified;
- the public parser accepts an in-memory `&[u8]` and the CLI reads the complete file into memory;
- metadata allocation scales with the number of actual frames and blocks, with no configurable resource limits yet;
- no continuous fuzz target yet; fuzzing remains required before a stable release;
- no formal 32-bit/WASM runtime support commitment yet;
- JSON and Rust public APIs remain pre-1.0 and may evolve intentionally;
- JavaScript-safe representation of all possible `u64` JSON values is deferred;
- the CLI package is not part of the initial crates.io publication path.

## Release-readiness conclusion

The original Issue #14 integration review was too permissive in several structural validation and release-gate areas. Issue #31 and PR #32 correct those findings rather than relying on the previous green tests as proof of specification conformance.

Once the final PR #32 CI run is green on all quality gates and all three supported desktop runner platforms, the implementation is suitable for the first **v0.1 library pre-release**. Merge and release remain explicit maintainer actions after review.
