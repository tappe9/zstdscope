## Representative CLI validation

The workspace test command executes integration tests that launch the compiled `zstdscope` binary with temporary files, providing the required end-to-end CLI validation rather than testing presentation helpers in isolation.

### Human-readable valid input

`crates/zstdscope-cli/tests/inspect_cli.rs::inspect_prints_a_readable_standard_frame_summary` executes the equivalent of:

```text
zstdscope inspect <valid.zst>
```

It uses an official-zstd-generated fixture and asserts Standard Frame/header/block/checksum output, including the `not verified` checksum wording.

### JSON valid input

`crates/zstdscope-cli/tests/json_cli.rs::json_standard_frame_has_explicit_snake_case_shape` executes the equivalent of:

```text
zstdscope inspect <valid.zst> --json
```

It parses stdout as JSON and asserts explicit snake_case field names, tagged `FrameKind`, block type, sizes, and checksum metadata.

### Malformed input

The text and JSON CLI suites execute the equivalent of:

```text
zstdscope inspect <malformed.zst>
zstdscope inspect <malformed.zst> --json
```

They assert non-zero exit status, empty stdout, and a typed parser diagnostic on stderr. The JSON path therefore cannot emit partial-success JSON on a parse failure.

## Fixture provenance

The durable integration corpus contains both official-reference and hand-built fixtures.

Reference fixtures were generated with the official Zstandard CLI v1.5.7 and have documented source bytes and regeneration commands under `crates/zstdscope/tests/fixtures/README.md`. Hand-built fixtures cover exact bit-level width, malformed-input, RLE, checksum, and mixed-stream cases.

## Known v0.1 limitations

These are deliberate boundaries, not release blockers:

- no compression or decompression;
- compressed block internals remain opaque;
- stored content checksums are not verified;
- the public parser accepts an in-memory `&[u8]`; the CLI reads the complete file into memory;
- no configurable frame/block count or memory resource limits yet;
- no continuous fuzz target is included in v0.1; targeted malformed/boundary tests enforce the current safety contract, while continuous fuzzing remains a hardening item before a stable release;
- JSON and Rust public APIs remain pre-1.0 and may evolve intentionally with documented changes.

The fuzzing limitation is consistent with `docs/REQUIREMENTS.md`, which requires fuzzing before the first stable release rather than the v0.1 MVP, and with the v0.2 roadmap candidate scope.

## Documentation synchronization

`README.md` already reflects the implemented parser, text CLI, JSON CLI, optional Serde, and current v0.1 scope.

`ROADMAP.md` is updated by this review to mark v0.1 as implemented and to make the absence of a continuous fuzz target explicit. The architecture's Fuzzing subsection remains the intended testing architecture/invariant; this review records that the target itself is future hardening rather than an implemented v0.1 artifact.

## Release-readiness conclusion

Subject to a green final review PR, the repository is coherent with the accepted v0.1 contract and is suitable for a first pre-release/version decision.

The remaining limitations are explicitly documented and belong to later milestones. No large missing v0.1 feature or undocumented architecture divergence was identified during this review.
