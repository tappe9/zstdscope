# ADR 0004: v0.1 public API and licensing policy

- Status: Accepted
- Date: 2026-08-18

## Context

The initial design PR intentionally left several public-facing choices unresolved. These choices affect encoded-data fidelity, future API compatibility, JSON consumers, dependency footprint, and contributor expectations.

ZstdScope is an inspector rather than a decompressor, so preserving how information is encoded is more important than normalizing fields purely for decompression semantics.

## Decision

### 1. License

ZstdScope is dual-licensed under **MIT OR Apache-2.0**, at the user's option.

The repository contains `LICENSE-MIT` and `LICENSE-APACHE`. Unless explicitly stated otherwise, contributions submitted for inclusion in ZstdScope are provided under the same dual-license terms.

### 2. Preserve encoded Dictionary ID zero

The API must distinguish these cases:

- the Dictionary ID field is absent;
- the field is present and encodes `0`;
- the field is present and encodes a non-zero ID.

Encoded zero has the same dictionary-ID meaning as an unspecified ID for decompression, but ZstdScope must not erase the byte-level distinction.

The preferred model is a field-specific value carrying both the encoded value and its source span, for example:

```rust
pub struct DictionaryId {
    pub encoded: u32,
    pub span: ByteSpan,
}
```

and `FrameHeader` uses `Option<DictionaryId>` so `None` means the field was absent while `Some(DictionaryId { encoded: 0, .. })` means zero was explicitly encoded.

### 3. Expose field-specific byte spans

v0.1 should expose `ByteSpan` information for frame-header fields that physically occur in the input, not only aggregate frame/header spans.

This includes, where present:

- magic number;
- frame-header descriptor;
- window descriptor;
- Dictionary ID;
- frame content size;
- block header and block content;
- content checksum;
- skippable frame size field and payload.

This supports the core Inspector use case and a future hex viewer without requiring a second parser pass.

### 4. `ZstdError` is non-exhaustive

`ZstdError` should use `#[non_exhaustive]` so future validation rules can introduce additional error variants without forcing downstream consumers to exhaustively match a permanently frozen error set.

Enums that directly mirror a closed set in the current Zstandard format, such as the public `BlockType` variants exposed by v0.1, should not automatically receive `#[non_exhaustive]`. Each public enum should be considered individually.

### 5. JSON uses `snake_case`

Machine-readable CLI output uses `snake_case` field names, matching Rust field naming. Before v1.0 the JSON schema may evolve, but changes must be documented once releases begin.

Examples:

```json
{
  "frame_content_size": 12345,
  "dictionary_id": 42,
  "content_checksum_flag": true
}
```

### 6. Keep the parser core dependency-light

The `zstdscope` core crate should keep mandatory dependencies to a minimum and must not depend on `libzstd`, `zstd-sys`, or other decompression implementations.

Serialization should be optional, with `serde` behind a Cargo feature. The CLI may depend on ergonomic libraries such as argument parsing and JSON serialization crates because those concerns are outside the parser core.

The intended direction is:

```toml
[features]
default = []
serde = ["dep:serde"]
```

The CLI enables the feature when JSON output is required.

## Consequences

### Positive

- ZstdScope preserves byte-level encoding details useful to inspection tooling.
- Future hex-viewer integration does not require redesigning the model around offsets.
- New error categories can be added with less downstream breakage.
- Rust and JSON field names remain easy to map mentally.
- Library consumers that only need parsing are not forced to pull in CLI or serialization dependencies.
- The dual license follows a common Rust ecosystem pattern and is friendly to commercial and open-source consumers.

### Trade-offs

- Field-specific spans make the public model somewhat larger.
- `#[non_exhaustive]` requires downstream error matches to include a fallback arm.
- Preserving encoded zero separately from an absent Dictionary ID is more verbose than semantic normalization.
- The dual-license setup requires maintaining both license files and clearly documenting contribution terms.

## Follow-up

The first implementation PR should encode these decisions directly in the public model and Cargo metadata rather than reopening them without a new ADR.
